Quality Attributes (QAs) referenced use the course taxonomy: **Usability, Performance, Availability, Reliability, Scalability, Security, Interoperability, Manageability, Supportability, Testability, Maintainability, Flexibility, Conceptual Integrity, Reusability**.

> Note on format: Each story ends with an explicit QA list: `[QAs: ...]`.

---

## User Stories (Grouped by Role)

### Planning fields

- **SP (Story Points)**: Fibonacci scale (1, 2, 3, 5, 8, 13) for relative effort.
- **Priority (MoSCoW)**: `Must` (MVP core), `Should` (MVP important), `Could` (post-MVP), `Won’t` (explicitly deferred).

## Customer

| ID | User Story | Acceptance Criteria | Quality Attributes | Justification | SP | Priority (MoSCoW) | Key Dependencies / Notes |
|---|---|---|---|---|---:|---|---|
| US-1 | **US-1 — Customer Registration/Login**: As a **Customer**, I want to **register and log in to the app**, so that **I can place and track orders with my profile**. **[QAs: Security, Usability, Availability]** | - Given I am not logged in, when I submit valid registration details, then my account is created and I can log in immediately.<br>- Given I enter invalid credentials, when I attempt to log in, then I am denied access and shown a clear error without exposing sensitive details.<br>- Given I am logged in, when I update my basic profile fields (e.g., display name, phone number), then changes are saved and reflected on my next app launch.<br>- Given the auth service is unavailable, when I attempt to log in, then I receive a retryable error and the app does not crash. | Security; Usability; Availability | - **Security**: Accounts protect personal/order data and prevent unauthorized access.<br>- **Usability**: Onboarding must be low-friction for broad user demographics.<br>- **Availability**: Login must work reliably to avoid blocking all downstream features. | 5 | Must | Foundation for identity, order ownership, and role-based actions. |
| US-2 | **US-2 — Browse/Search Restaurants**: As a **Customer**, I want to **discover restaurants and browse menus**, so that **I can quickly find food to order**. **[QAs: Performance, Usability, Scalability]** | - Given I open the restaurant list, when data is available, then the first page renders within a defined threshold (e.g., ≤ 2 seconds on typical mobile network conditions).<br>- Given I search by name/category, when I submit a query, then I receive results matching the query and can open a restaurant detail view.<br>- Given there are many restaurants, when I scroll, then pagination/continuous loading works without app freeze. | Performance; Usability; Scalability | - **Performance**: Search/browse speed directly impacts BO-1 (reduce ordering time).<br>- **Usability**: Discovery is the primary customer journey and must be intuitive.<br>- **Scalability**: As the restaurant catalog and concurrent searches grow, the system can scale (e.g., indexing/caching/scale-out) while still meeting the same response-time SLA (the performance target above). | 5 | Must | Depends on restaurant onboarding (US-10/US-18) and menu data (US-11). |
| US-3 | **US-3 — Search/Filter Food Items by Category & Proximity (MVP)**: As a **Customer**, I want to **search and filter menu items by category and proximity**, so that **I can quickly find suitable food that can be delivered to my address**. **[QAs: Performance, Usability, Reliability, Interoperability, Scalability]** | - Given I have provided a delivery location (GPS permission granted or a manually entered address), when I open item search, then the system uses that location for proximity filtering.<br>- Given I enter a keyword and/or select a food category, when I search, then the results contain only menu items that match the query and are offered by restaurants within deliverable distance for my location (BR-3).<br>- Given results are returned, then each result displays at minimum item name, item price, restaurant name, and an indication of proximity (e.g., distance or “within radius”).<br>- Given I tap a result, then I can navigate to the owning restaurant/menu detail view to continue ordering (consistent with single-restaurant ordering flow, BR-2).<br>- Given the item search backend is available, when I submit a query, then the first page of results returns within a defined threshold (e.g., p95 ≤ 2 seconds under normal conditions) and supports pagination.<br>- Given location cannot be resolved (no permission and no address), when I attempt proximity filtering, then the UI requests an address or permission and does not return misleading proximity-based results. | Performance; Usability; Reliability; Interoperability; Scalability | - **Performance**: Search must feel responsive to reduce time-to-order (BO-1).<br>- **Usability**: Item-first search is a common discovery path and should minimize taps.<br>- **Reliability**: Incorrect deliverability/proximity filtering causes failed checkouts and frustration (BR-3).<br>- **Interoperability**: Depends on geolocation/geocoding and distance calculations (Vision dependencies).<br>- **Scalability**: As restaurant/menu inventory (catalog size) and concurrent searches grow, the system can scale (e.g., indexing/caching/scale-out) while still meeting the p95 ≤ 2 seconds first-page SLA and an acceptable error rate. | 8 | Should | Depends on deliverability/location (US-6) and stable menu/catalog. |
| US-4 | **US-4 — View Restaurant Availability**: As a **Customer**, I want to **see whether a restaurant/menu item is available**, so that **I do not waste time ordering unavailable items**. **[QAs: Reliability, Usability]** | - Given a restaurant is marked Closed/Unavailable, when I open it, then the UI clearly indicates unavailability and blocks adding items to cart.<br>- Given a menu item is marked Sold Out, when I view the menu, then the item is not addable to cart.<br>- Given availability changes while I browse, when the change is received, then the UI updates within a defined window (e.g., ≤ 10 seconds) or on refresh. | Reliability; Usability | - **Reliability**: Availability state must be correct to avoid failed orders and user frustration (BR-8).<br>- **Usability**: Clear visibility prevents confusion and repeated attempts. | 3 | Must | Depends on partner availability controls (US-12). |
| US-5 | **US-5 — Single-Restaurant Cart Constraint**: As a **Customer**, I want my **cart restricted to one restaurant**, so that **checkout and fulfillment remain consistent**. **[QAs: Conceptual Integrity, Usability, Testability]** | - Given my cart contains items from Restaurant A, when I attempt to add an item from Restaurant B, then the system blocks it and explains options (clear cart or cancel) (BR-2).<br>- Given I choose to clear the cart, when I confirm, then all items are removed and I can add items from Restaurant B.<br>- Given I cancel, then the cart remains unchanged. | Conceptual Integrity; Usability; Testability | - **Conceptual Integrity**: Enforces a consistent domain model (one order ↔ one restaurant).<br>- **Usability**: Prevents silent failures; provides a clear decision path.<br>- **Testability**: Rule is discrete and must be verifiable via deterministic tests. | 2 | Must | Enforced by cart (US-22) and checkout (US-7). |
| US-6 | **US-6 — Delivery Address Within Radius**: As a **Customer**, I want to **confirm my delivery address is serviceable**, so that **my order can be accepted and delivered**. **[QAs: Reliability, Interoperability, Usability]** | - Given I enter a delivery address, when I validate it, then the system confirms whether it is within the restaurant’s delivery radius (BR-3).<br>- Given the address is outside the radius, when I attempt checkout, then checkout is blocked with a specific reason.<br>- Given the map/geocoding provider is unavailable, when I validate the address, then I receive an actionable error and can retry. | Reliability; Interoperability; Usability | - **Reliability**: Prevents orders that cannot be fulfilled (reduces cancellations).<br>- **Interoperability**: Typically depends on map/geocoding APIs (Vision dependencies).<br>- **Usability**: Clear feedback avoids repeated failed checkouts. | 5 | Must | Depends on map/geocoding/distance capability; ties to BR-3 and service area policy (US-20). |
| US-7 | **US-7 — Checkout With COD or VNPay (MVP)**: As a **Customer**, I want to **place an order using COD or VNPay**, so that **I can complete purchases with my preferred payment method**. **[QAs: Security, Usability, Reliability, Interoperability, Flexibility]** | - Given I have items in my cart, when I proceed to checkout, then I can select either COD or VNPay as the payment method (BR-4).<br>- Given I select COD, when I confirm the order, then an order record is created with status `Pending` and an order ID is returned.<br>- Given I select VNPay, when I confirm the order, then the system initiates the VNPay payment flow and only creates/routes the order after receiving a successful payment confirmation from VNPay (BR-4).<br>- Given VNPay payment fails or is cancelled, when the VNPay flow returns to the app, then the order is not routed and the user sees a clear failure/cancellation state with a retry option.<br>- Given I retry the same checkout with the same client idempotency key within a configured TTL (e.g., `ORDER_IDEMPOTENCY_TTL_MINUTES`), when the request reaches the backend, then the system returns the same order ID and does not create a duplicate order. | Security; Usability; Reliability; Interoperability; Flexibility | - **Security**: Online payment introduces sensitive transaction and callback handling requirements.<br>- **Usability**: Customers need a clear, low-friction choice between COD and VNPay.<br>- **Reliability**: Must prevent duplicates and inconsistent order/payment states.<br>- **Interoperability**: Requires integration with an external payment gateway (VNPay).<br>- **Flexibility**: Payment methods are expected to evolve; the checkout supports adding a new payment provider via a localized provider/adapter + configuration (without redesigning the core checkout workflow/state model). | 13 | Must | Depends on cart (US-22), constraints (US-5), deliverability (US-6), and lifecycle (US-8). VNPay requires gateway integration and confirmation handling. |
| US-9 | **US-9 — Real-Time Order Status Updates**: As a **Customer**, I want to **receive real-time order status updates**, so that **I can track progress without repeatedly refreshing**. **[QAs: Availability, Performance, Interoperability]** | - Given my order status changes, when the backend publishes an update, then my app receives the update within a defined SLA (e.g., ≤ 5 seconds under normal conditions).<br>- Given the app is in the background or closed, when a critical status update occurs, then the system delivers a push notification via APNs/FCM and the app reflects the latest status on next open (FR-2.3).<br>- Given the real-time channel disconnects, when reconnect occurs, then the app resynchronizes status to the latest state.<br>- Given push/WebSocket providers are degraded, then the system falls back to periodic polling without breaking the app. | Availability; Performance; Interoperability | - **Availability**: Real-time tracking depends on continuous connectivity (Vision dependency DE-2).<br>- **Performance**: Updates must be timely to be meaningful to users.<br>- **Interoperability**: Integrates with push (APNs/FCM) and/or WebSocket infrastructure. | 8 | Must | Depends on lifecycle events (US-8) and updates from restaurant/shipper actions (US-13, US-16, US-17, US-23). |
| US-22 | **US-22 — Shopping Cart Management (MVP)**: As a **Customer**, I want to **add/remove items and adjust quantities in my cart**, so that **I can review my order before checkout**. **[QAs: Usability, Reliability, Performance]** | - Given I am viewing a menu item, when I add it to my cart with a quantity, then the cart updates and the running total is recalculated.<br>- Given my cart contains an item, when I increase/decrease quantity or remove the item, then the cart updates immediately and totals reflect the change.<br>- Given I leave and reopen the app, when I return to the cart, then the cart contents remain available (within a configured persistence window) or I am clearly informed the cart was reset.<br>- Given my cart contains items from one restaurant, when I attempt to add an item from a different restaurant, then the system enforces the single-restaurant constraint as defined in US-5 (BR-2). | Usability; Reliability; Performance | - **Usability**: Cart operations are high-frequency actions that must be simple and fast.<br>- **Reliability**: Prevents mismatched totals/quantities that cause failed checkouts and disputes.<br>- **Performance**: Cart recalculation must feel instantaneous on mobile devices. | 5 | Must | Depends on menu/catalog (US-11) and rule enforcement (US-5). |

## Restaurant Partner

| ID | User Story | Acceptance Criteria | Quality Attributes | Justification | SP | Priority (MoSCoW) | Key Dependencies / Notes |
|---|---|---|---|---|---:|---|---|
| US-10 | **US-10 — Restaurant Onboarding Approval**: As a **Restaurant Partner**, I want to **be approved by an Admin**, so that **I can start receiving orders**. **[QAs: Security, Manageability, Supportability]** | - Given I register as a restaurant partner, when submission completes, then my account is set to `Pending Approval` (BR-1).<br>- Given an admin approves me, then my account becomes `Active` and can receive orders.<br>- Given an admin rejects me, then my account remains inactive and I receive a reason code/message. | Security; Manageability; Supportability | - **Security**: Prevents fraudulent providers from operating on the platform (BR-1).<br>- **Manageability**: Admins need controlled workflows to govern the marketplace.<br>- **Supportability**: Decision reasons reduce support tickets and improve traceability. | 5 | Must | Depends on admin access + approvals (US-25, US-18). |
| US-11 | **US-11 — Restaurant Menu Management**: As a **Restaurant Partner**, I want to **create and update menu items**, so that **customers can order current offerings**. **[QAs: Maintainability, Usability, Reliability]** | - Given I create a menu item with required fields, when I save, then it becomes visible to customers.<br>- Given I edit price/name/availability, when I save, then changes propagate to customer browsing within a defined window (e.g., ≤ 60 seconds).<br>- Given invalid fields (e.g., negative price), when I save, then the system rejects the update with validation errors. | Maintainability; Usability; Reliability | - **Maintainability**: Because menu business rules and item attributes evolve, the menu-management module/data model can be changed with localized impact (minimal modules touched) and low regression risk, so new fields/rules can be delivered safely without widespread refactoring.<br>- **Usability**: Restaurant staff operate under pressure; workflows must be efficient (SRS persona).<br>- **Reliability**: Customers must see accurate menu data to avoid fulfillment issues. | 8 | Must | Enables customer browse + cart (US-2, US-22). |
| US-12 | **US-12 — Restaurant Real-Time Availability Control**: As a **Restaurant Partner**, I want to **mark items/restaurant as sold out/closed**, so that **new orders are prevented immediately**. **[QAs: Reliability, Performance]** | - Given I toggle a menu item to `Sold Out`, when saved, then customers cannot add it to cart (BR-8).<br>- Given I mark the restaurant `Closed`, when saved, then customers cannot place new orders and see the closed state (BR-8).<br>- Given the system is under peak load, when I update availability, then the update is applied within a defined SLA (e.g., ≤ 10 seconds). | Reliability; Performance | - **Reliability**: Prevents orders that cannot be prepared (BR-8).<br>- **Performance**: Availability toggles must take effect quickly to avoid race conditions. | 5 | Must | Drives customer availability visibility (US-4) and prevents invalid orders. |
| US-13 | **US-13 — Accept/Reject Incoming Orders**: As a **Restaurant Partner**, I want to **receive and accept orders**, so that **I can start preparation**. **[QAs: Availability, Usability, Performance]** | - Given an order is placed, when it is routed to my restaurant, then I receive a notification and can open the order details.<br>- Given a new order arrives, then the system generates a prominent auditory + visual alert that persists until acknowledged (FR-3.3).<br>- Given I accept an order, then status becomes `Accepted` and the customer is notified within the defined SLA.<br>- Given I do not accept or reject within a configured timeout (e.g., `RESTAURANT_ACCEPT_TIMEOUT_SECONDS`), when the timeout elapses, then the order is marked `Unaccepted/Expired` and the customer is notified with a specific reason code. | Availability; Usability; Performance | - **Availability**: Missed orders impact revenue and user trust.<br>- **Usability**: Kitchen environment requires minimal taps and clear actions (SRS persona).<br>- **Performance**: Notifications/status propagation must be fast for real-time flow. | 8 | Must | Depends on checkout creating/routing orders (US-7) and lifecycle enforcement (US-8). |
| US-23 | **US-23 — Restaurant Update Preparation Status (MVP)**: As a **Restaurant Partner**, I want to **update the preparation status of accepted orders**, so that **customers and shippers have accurate readiness information**. **[QAs: Reliability, Usability, Performance]** | - Given I have accepted an order, when I start cooking, then I can mark it as `Preparing` and the customer receives an update within the defined SLA.<br>- Given an order is `Preparing`, when it is ready to hand off, then I can mark it `Ready for Pickup` and the customer/shipper receive an update within the defined SLA.<br>- Given an order is not in the expected prior state, when I attempt a status transition, then the system rejects the change as out-of-sequence (BR-7). | Reliability; Usability; Performance | - **Reliability**: Accurate prep readiness reduces failed pickups and customer complaints.<br>- **Usability**: Kitchen workflows must be quick, low-tap, and hard to misuse.<br>- **Performance**: Prep-status changes must propagate quickly so the tracking view stays meaningful. | 3 | Should | Depends on lifecycle (US-8) and customer tracking/notifications (US-9). |
| US-24 | **US-24 — Restaurant Cancel Order With Reason (MVP)**: As a **Restaurant Partner**, I want to **cancel an order with a clear reason**, so that **customers are informed and operations stay consistent**. **[QAs: Reliability, Supportability, Usability]** | - Given an order is not yet `Picked Up`, when I cancel it, then a cancellation reason is required and the system records the actor and timestamp.<br>- Given an order is canceled by the restaurant, then the customer is notified immediately and sees the cancellation reason (FR-2.4).<br>- Given an order is already `Picked Up` or `Delivered`, when I attempt cancellation, then the system blocks the action with a clear message. | Reliability; Supportability; Usability | - **Reliability**: Prevents inconsistent lifecycle states and incorrect tracking outcomes.<br>- **Supportability**: Captured reasons reduce manual investigation and support burden.<br>- **Usability**: Clear cancellation flows reduce confusion during peak operations. | 3 | Should | Depends on lifecycle constraints (US-8) and notification surface to customers (US-9). |

## Shipper (Delivery Personnel)

| ID | User Story | Acceptance Criteria | Quality Attributes | Justification | SP | Priority (MoSCoW) | Key Dependencies / Notes |
|---|---|---|---|---|---:|---|---|
| US-14 | **US-14 — Shipper Onboarding Approval**: As a **Delivery Personnel (Shipper)**, I want to **be approved by an Admin**, so that **I can receive delivery jobs**. **[QAs: Security, Manageability, Supportability]** | - Given I register as a shipper, when submission completes, then my account is `Pending Approval` (BR-1).<br>- Given an admin approves, then I can toggle availability and receive dispatch requests.<br>- Given an admin rejects, then I cannot receive jobs and I receive a reason. | Security; Manageability; Supportability | - **Security**: Prevents misuse and protects customers and restaurants.<br>- **Manageability**: Admin oversight is required by business rules (BR-1).<br>- **Supportability**: Reason codes help address issues efficiently. | 3 | Must | Depends on admin access + approvals (US-25, US-18). |
| US-15 | **US-15 — Shipper Availability Toggle**: As a **Shipper**, I want to **set myself available/unavailable**, so that **I only receive orders when I’m ready to deliver**. **[QAs: Usability, Reliability, Performance]** | - Given I set status to `Available`, then I become eligible to receive dispatch requests within a defined SLA (e.g., ≤ 10 seconds).<br>- Given I set status to `Unavailable`, then I stop receiving new dispatch requests immediately (or within SLA).<br>- Given intermittent connectivity, when I change status, then the app confirms whether the change is synced or queued. | Usability; Reliability; Performance | - **Usability**: Must be simple for on-the-move workers.<br>- **Reliability**: Prevents dispatching to unavailable shippers, improving delivery success (BO-3).<br>- **Performance**: Quick propagation avoids wasted time during peaks. | 3 | Must | Needed before dispatch/assignment can be meaningful. |
| US-16 | **US-16 — Shipper Accept & Pick Up Order**: As a **Shipper**, I want to **accept a delivery job and confirm pickup**, so that **the customer can track the delivery accurately**. **[QAs: Reliability, Security, Interoperability]** | - Given I receive a dispatch request, when I accept, then the order is assigned to me and cannot be assigned to another shipper simultaneously.<br>- Given I arrive at the restaurant, when I confirm pickup, then order status transitions to `Picked Up` (part of BR-7 lifecycle).<br>- Given my app cannot reach the server, when I attempt to confirm pickup, then the system does not transition the order state and the app shows a retryable error message. | Reliability; Security; Interoperability | - **Reliability**: Prevents double-assignment and ensures correct tracking state.<br>- **Security**: Only the assigned shipper should be able to update pickup/delivery status.<br>- **Interoperability**: Often integrates with maps/GPS/location services (Vision dependency DE-1). | 5 | Must | Depends on order dispatch/assignment logic and lifecycle (US-8). |
| US-17 | **US-17 — Shipper Confirm Delivery**: As a **Shipper**, I want to **confirm successful delivery**, so that **the order can be closed and metrics can be tracked**. **[QAs: Reliability, Security, Supportability]** | - Given I am assigned to the order, when I confirm delivery, then status becomes `Delivered` and is visible to customer/admin (BR-7).<br>- Given the order is not in `Picked Up`, when I attempt confirm delivery, then the system rejects the transition (BR-7).<br>- Given my app cannot reach the server, when I attempt to confirm delivery, then the system does not transition the order state and the app shows a retryable error message.<br>- Given delivery is confirmed, then the system records timestamp and actor identity for traceability. | Reliability; Security; Supportability | - **Reliability**: Correct closure prevents disputes and incorrect KPIs.<br>- **Security**: Prevents unauthorized completion of orders.<br>- **Supportability**: Audit trail supports issue resolution and compliance needs. | 3 | Must | Completes the end-to-end order flow; depends on lifecycle (US-8). |

## Notes (configuration-based measurability)

Several acceptance criteria use **configuration-based thresholds** (timeouts, SLAs, “stuck” detection). This keeps them measurable/testable while letting you tune values during MVP.

You can finalize and document these configuration values for your project:
- Notification/real-time SLAs per role and network baseline.
- Restaurant accept timeout and per-status “stuck” thresholds.
- Service area boundary representation (polygon, radius, administrative region).
