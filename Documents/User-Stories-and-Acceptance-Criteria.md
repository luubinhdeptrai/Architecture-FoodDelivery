Quality Attributes (QAs) referenced use the course taxonomy: **Usability, Performance, Availability, Reliability, Scalability, Security, Interoperability, Manageability, Supportability, Testability, Maintainability, Flexibility, Conceptual Integrity, Reusability**.

> Note on format: Each story ends with an explicit QA list: `[QAs: ...]`.

## User Stories Table

| User Story | Acceptance Criteria | Quality Attributes | Justification |
|---|---|---|---|
| **US-1 — Customer Registration/Login**: As a **Customer**, I want to **register and log in to the app**, so that **I can place and track orders with my profile**. **[QAs: Security, Usability, Availability]** | - Given I am not logged in, when I submit valid registration details, then my account is created and I can log in immediately.<br>- Given I enter invalid credentials, when I attempt to log in, then I am denied access and shown a clear error without exposing sensitive details.<br>- Given the auth service is unavailable, when I attempt to log in, then I receive a retryable error and the app does not crash. | Security; Usability; Availability | - **Security**: Accounts protect personal/order data and prevent unauthorized access.<br>- **Usability**: Onboarding must be low-friction for broad user demographics.<br>- **Availability**: Login must work reliably to avoid blocking all downstream features. |
| **US-2 — Browse/Search Restaurants**: As a **Customer**, I want to **discover restaurants and browse menus**, so that **I can quickly find food to order**. **[QAs: Performance, Usability, Scalability]** | - Given I open the restaurant list, when data is available, then the first page renders within a defined threshold (e.g., ≤ 2 seconds on typical mobile network conditions).<br>- Given I search by name/category, when I submit a query, then I receive results matching the query and can open a restaurant detail view.<br>- Given there are many restaurants, when I scroll, then pagination/continuous loading works without app freeze. | Performance; Usability; Scalability | - **Performance**: Search/browse speed directly impacts BO-1 (reduce ordering time).<br>- **Usability**: Discovery is the primary customer journey and must be intuitive.<br>- **Scalability**: Catalog growth must not degrade responsiveness. |
| **US-3 — Search/Filter Food Items by Category & Proximity (MVP)**: As a **Customer**, I want to **search and filter menu items by category and proximity**, so that **I can quickly find suitable food that can be delivered to my address**. **[QAs: Performance, Usability, Reliability, Interoperability, Scalability]** | - Given I have provided a delivery location (GPS permission granted or a manually entered address), when I open item search, then the system uses that location for proximity filtering.<br>- Given I enter a keyword and/or select a food category, when I search, then the results contain only menu items that match the query and are offered by restaurants within deliverable distance for my location (BR-3).<br>- Given results are returned, then each result displays at minimum item name, item price, restaurant name, and an indication of proximity (e.g., distance or “within radius”).<br>- Given I tap a result, then I can navigate to the owning restaurant/menu detail view to continue ordering (consistent with single-restaurant ordering flow, BR-2).<br>- Given the item search backend is available, when I submit a query, then the first page of results returns within a defined threshold (e.g., p95 ≤ 2 seconds under normal conditions) and supports pagination.<br>- Given location cannot be resolved (no permission and no address), when I attempt proximity filtering, then the UI requests an address or permission and does not return misleading proximity-based results. | Performance; Usability; Reliability; Interoperability; Scalability | - **Performance**: Search must feel responsive to reduce time-to-order (BO-1).<br>- **Usability**: Item-first search is a common discovery path and should minimize taps.<br>- **Reliability**: Incorrect deliverability/proximity filtering causes failed checkouts and frustration (BR-3).<br>- **Interoperability**: Depends on geolocation/geocoding and distance calculations (Vision dependencies).<br>- **Scalability**: Must perform well as menu inventory and restaurants grow. |
| **US-4 — View Restaurant Availability**: As a **Customer**, I want to **see whether a restaurant/menu item is available**, so that **I do not waste time ordering unavailable items**. **[QAs: Reliability, Usability]** | - Given a restaurant is marked Closed/Unavailable, when I open it, then the UI clearly indicates unavailability and blocks adding items to cart.<br>- Given a menu item is marked Sold Out, when I view the menu, then the item is not addable to cart.<br>- Given availability changes while I browse, when the change is received, then the UI updates within a defined window (e.g., ≤ 10 seconds) or on refresh. | Reliability; Usability | - **Reliability**: Availability state must be correct to avoid failed orders and user frustration (BR-8).<br>- **Usability**: Clear visibility prevents confusion and repeated attempts. |
| **US-5 — Single-Restaurant Cart Constraint**: As a **Customer**, I want my **cart restricted to one restaurant**, so that **checkout and fulfillment remain consistent**. **[QAs: Conceptual Integrity, Usability, Testability]** | - Given my cart contains items from Restaurant A, when I attempt to add an item from Restaurant B, then the system blocks it and explains options (clear cart or cancel) (BR-2).<br>- Given I choose to clear the cart, when I confirm, then all items are removed and I can add items from Restaurant B.<br>- Given I cancel, then the cart remains unchanged. | Conceptual Integrity; Usability; Testability | - **Conceptual Integrity**: Enforces a consistent domain model (one order ↔ one restaurant).<br>- **Usability**: Prevents silent failures; provides a clear decision path.<br>- **Testability**: Rule is discrete and must be verifiable via deterministic tests. |
| **US-6 — Delivery Address Within Radius**: As a **Customer**, I want to **confirm my delivery address is serviceable**, so that **my order can be accepted and delivered**. **[QAs: Reliability, Interoperability, Usability]** | - Given I enter a delivery address, when I validate it, then the system confirms whether it is within the restaurant’s delivery radius (BR-3).<br>- Given the address is outside the radius, when I attempt checkout, then checkout is blocked with a specific reason.<br>- Given the map/geocoding provider is unavailable, when I validate the address, then I receive an actionable error and can retry. | Reliability; Interoperability; Usability | - **Reliability**: Prevents orders that cannot be fulfilled (reduces cancellations).<br>- **Interoperability**: Typically depends on map/geocoding APIs (Vision dependencies).<br>- **Usability**: Clear feedback avoids repeated failed checkouts. |
| **US-7 — Checkout With COD or VNPay (MVP)**: As a **Customer**, I want to **place an order using COD or VNPay**, so that **I can complete purchases with my preferred payment method**. **[QAs: Security, Usability, Reliability, Interoperability]** | - Given I have items in my cart, when I proceed to checkout, then I can select either COD or VNPay as the payment method (BR-4).<br>- Given I select COD, when I confirm the order, then an order record is created with status `Pending` and an order ID is returned.<br>- Given I select VNPay, when I confirm the order, then the system initiates the VNPay payment flow and only creates/routes the order after receiving a successful payment confirmation from VNPay (BR-4).<br>- Given VNPay payment fails or is cancelled, when the VNPay flow returns to the app, then the order is not routed and the user sees a clear failure/cancellation state with a retry option.<br>- Given I retry the same checkout with the same client idempotency key within a configured TTL (e.g., `ORDER_IDEMPOTENCY_TTL_MINUTES`), when the request reaches the backend, then the system returns the same order ID and does not create a duplicate order. | Security; Usability; Reliability; Interoperability | - **Security**: Online payment introduces sensitive transaction and callback handling requirements.<br>- **Usability**: Customers need a clear, low-friction choice between COD and VNPay.<br>- **Reliability**: Must prevent duplicates and inconsistent order/payment states.<br>- **Interoperability**: Requires integration with an external payment gateway (VNPay). |
| **US-8 — Order Lifecycle Integrity**: As a **Platform**, I want **orders to progress through strict statuses**, so that **tracking is accurate and operations stay consistent**. **[QAs: Reliability, Maintainability, Testability]** | - Given an order is `Pending`, when a restaurant accepts it, then status becomes `Accepted`.<br>- Given an order is `Accepted`, when preparation starts, then status becomes `Preparing`.<br>- Given an order is `Preparing`, when it is ready, then status becomes `Ready for Pickup/Picked Up`.<br>- Given an order is `Picked Up`, when delivered is confirmed, then status becomes `Delivered`.<br>- Given a user attempts an out-of-sequence transition, then the system rejects it with a specific error (BR-7). | Reliability; Maintainability; Testability | - **Reliability**: Prevents inconsistent state and incorrect tracking (BR-7).<br>- **Maintainability**: A clear finite-state model reduces future change risk.<br>- **Testability**: State machine transitions are straightforward to unit/integration test. |
| **US-9 — Real-Time Order Status Updates**: As a **Customer**, I want to **receive real-time order status updates**, so that **I can track progress without repeatedly refreshing**. **[QAs: Availability, Performance, Interoperability]** | - Given my order status changes, when the backend publishes an update, then my app receives the update within a defined SLA (e.g., ≤ 5 seconds under normal conditions).<br>- Given the real-time channel disconnects, when reconnect occurs, then the app resynchronizes status to the latest state.<br>- Given push/WebSocket providers are degraded, then the system falls back to periodic polling without breaking the app. | Availability; Performance; Interoperability | - **Availability**: Real-time tracking depends on continuous connectivity (Vision dependency DE-2).<br>- **Performance**: Updates must be timely to be meaningful to users.<br>- **Interoperability**: Integrates with push (APNs/FCM) and/or WebSocket infrastructure. |
| **US-10 — Restaurant Onboarding Approval**: As a **Restaurant Partner**, I want to **be approved by an Admin**, so that **I can start receiving orders**. **[QAs: Security, Manageability, Supportability]** | - Given I register as a restaurant partner, when submission completes, then my account is set to `Pending Approval` (BR-1).<br>- Given an admin approves me, then my account becomes `Active` and can receive orders.<br>- Given an admin rejects me, then my account remains inactive and I receive a reason code/message. | Security; Manageability; Supportability | - **Security**: Prevents fraudulent providers from operating on the platform (BR-1).<br>- **Manageability**: Admins need controlled workflows to govern the marketplace.<br>- **Supportability**: Decision reasons reduce support tickets and improve traceability. |
| **US-11 — Restaurant Menu Management**: As a **Restaurant Partner**, I want to **create and update menu items**, so that **customers can order current offerings**. **[QAs: Maintainability, Usability, Reliability]** | - Given I create a menu item with required fields, when I save, then it becomes visible to customers.<br>- Given I edit price/name/availability, when I save, then changes propagate to customer browsing within a defined window (e.g., ≤ 60 seconds).<br>- Given invalid fields (e.g., negative price), when I save, then the system rejects the update with validation errors. | Maintainability; Usability; Reliability | - **Maintainability**: Menus change frequently; updates must be safe and low-cost to manage.<br>- **Usability**: Restaurant staff operate under pressure; workflows must be efficient (SRS persona).<br>- **Reliability**: Customers must see accurate menu data to avoid fulfillment issues. |
| **US-12 — Restaurant Real-Time Availability Control**: As a **Restaurant Partner**, I want to **mark items/restaurant as sold out/closed**, so that **new orders are prevented immediately**. **[QAs: Reliability, Performance, Availability]** | - Given I toggle a menu item to `Sold Out`, when saved, then customers cannot add it to cart (BR-8).<br>- Given I mark the restaurant `Closed`, when saved, then customers cannot place new orders and see the closed state (BR-8).<br>- Given the system is under peak load, when I update availability, then the update is applied within a defined SLA (e.g., ≤ 10 seconds). | Reliability; Performance; Availability | - **Reliability**: Prevents orders that cannot be prepared (BR-8).<br>- **Performance**: Availability toggles must take effect quickly to avoid race conditions.<br>- **Availability**: Restaurant operations depend on being able to control intake. |
| **US-13 — Accept/Reject Incoming Orders**: As a **Restaurant Partner**, I want to **receive and accept orders**, so that **I can start preparation**. **[QAs: Availability, Usability, Performance]** | - Given an order is placed, when it is routed to my restaurant, then I receive a notification and can open the order details.<br>- Given I accept an order, then status becomes `Accepted` and the customer is notified within the defined SLA.<br>- Given I do not accept or reject within a configured timeout (e.g., `RESTAURANT_ACCEPT_TIMEOUT_SECONDS`), when the timeout elapses, then the order is marked `Unaccepted/Expired` and the customer is notified with a specific reason code. | Availability; Usability; Performance | - **Availability**: Missed orders impact revenue and user trust.<br>- **Usability**: Kitchen environment requires minimal taps and clear actions (SRS persona).<br>- **Performance**: Notifications/status propagation must be fast for real-time flow. |
| **US-14 — Shipper Onboarding Approval**: As a **Delivery Personnel (Shipper)**, I want to **be approved by an Admin**, so that **I can receive delivery jobs**. **[QAs: Security, Manageability, Supportability]** | - Given I register as a shipper, when submission completes, then my account is `Pending Approval` (BR-1).<br>- Given an admin approves, then I can toggle availability and receive dispatch requests.<br>- Given an admin rejects, then I cannot receive jobs and I receive a reason. | Security; Manageability; Supportability | - **Security**: Prevents misuse and protects customers and restaurants.<br>- **Manageability**: Admin oversight is required by business rules (BR-1).<br>- **Supportability**: Reason codes help address issues efficiently. |
| **US-15 — Shipper Availability Toggle**: As a **Shipper**, I want to **set myself available/unavailable**, so that **I only receive orders when I’m ready to deliver**. **[QAs: Usability, Reliability, Performance]** | - Given I set status to `Available`, then I become eligible to receive dispatch requests within a defined SLA (e.g., ≤ 10 seconds).<br>- Given I set status to `Unavailable`, then I stop receiving new dispatch requests immediately (or within SLA).<br>- Given intermittent connectivity, when I change status, then the app confirms whether the change is synced or queued. | Usability; Reliability; Performance | - **Usability**: Must be simple for on-the-move workers.<br>- **Reliability**: Prevents dispatching to unavailable shippers, improving delivery success (BO-3).<br>- **Performance**: Quick propagation avoids wasted time during peaks. |
| **US-16 — Shipper Accept & Pick Up Order**: As a **Shipper**, I want to **accept a delivery job and confirm pickup**, so that **the customer can track the delivery accurately**. **[QAs: Reliability, Security, Interoperability]** | - Given I receive a dispatch request, when I accept, then the order is assigned to me and cannot be assigned to another shipper simultaneously.<br>- Given I arrive at the restaurant, when I confirm pickup, then order status transitions to `Picked Up` (part of BR-7 lifecycle).<br>- Given my app cannot reach the server, when I attempt to confirm pickup, then the system does not transition the order state and the app shows a retryable error message. | Reliability; Security; Interoperability | - **Reliability**: Prevents double-assignment and ensures correct tracking state.<br>- **Security**: Only the assigned shipper should be able to update pickup/delivery status.<br>- **Interoperability**: Often integrates with maps/GPS/location services (Vision dependency DE-1). |
| **US-17 — Shipper Confirm Delivery**: As a **Shipper**, I want to **confirm successful delivery**, so that **the order can be closed and metrics can be tracked**. **[QAs: Reliability, Security, Supportability]** | - Given I am assigned to the order, when I confirm delivery, then status becomes `Delivered` and is visible to customer/admin (BR-7).<br>- Given the order is not in `Picked Up`, when I attempt confirm delivery, then the system rejects the transition (BR-7).<br>- Given my app cannot reach the server, when I attempt to confirm delivery, then the system does not transition the order state and the app shows a retryable error message.<br>- Given delivery is confirmed, then the system records timestamp and actor identity for traceability. | Reliability; Security; Supportability | - **Reliability**: Correct closure prevents disputes and incorrect KPIs.<br>- **Security**: Prevents unauthorized completion of orders.<br>- **Supportability**: Audit trail supports issue resolution and compliance needs. |
| **US-18 — Admin Approve/Reject Partners**: As a **System Administrator**, I want to **review and approve/reject restaurant and shipper applications**, so that **the marketplace remains trustworthy and safe**. **[QAs: Security, Manageability, Usability]** | - Given a new application exists, when I open the admin dashboard, then I can view a queue of `Pending Approval` accounts (BR-1).<br>- Given I approve or reject, then the decision takes effect immediately and notifies the applicant.<br>- Given I lack sufficient permissions, when I attempt to approve/reject, then the system denies the action. | Security; Manageability; Usability | - **Security**: Core governance control to prevent fraud and abuse.<br>- **Manageability**: Admin workflows are required to operate the platform at scale.<br>- **Usability**: Admins need efficient review flows to avoid operational bottlenecks. |
| **US-19 — Admin Monitor Order/Platform Health (MVP)**: As a **System Administrator**, I want to **monitor order statuses and basic operational metrics**, so that **I can detect issues early and support operations**. **[QAs: Supportability, Manageability, Availability]** | - Given I access the dashboard, when the system is healthy, then I can view current orders grouped by status and basic counts (e.g., Pending/Accepted/Delivering/Delivered).<br>- Given an order remains in the same status beyond a configured threshold (e.g., `Preparing` longer than `ORDER_STUCK_THRESHOLD_SECONDS_PREPARING`), when the threshold is exceeded, then it is flagged for review with a reason code indicating the threshold that was breached.<br>- Given the monitoring view loads, then it shows data updated within a defined freshness window (e.g., ≤ 60 seconds). | Supportability; Manageability; Availability | - **Supportability**: Enables faster debugging and issue resolution (course definition).<br>- **Manageability**: Operators need tools to tune and intervene in processes.<br>- **Availability**: Operational visibility is critical during incidents. |
| **US-20 — Geographic Scope Restriction (MVP)**: As a **Platform**, I want to **restrict ordering to a single service area**, so that **MVP operations remain controlled and feasible**. **[QAs: Conceptual Integrity, Reliability, Maintainability]** | - Given a customer address is outside the configured service area, when they attempt to place an order, then the system blocks order submission (BR-6).<br>- Given the service area definition changes, when configuration is updated, then the new boundary takes effect without code changes (if configuration-based).<br>- Given the same address is checked repeatedly, results are consistent across sessions. | Conceptual Integrity; Reliability; Maintainability | - **Conceptual Integrity**: Keeps MVP scope consistent with stated limitations (BR-6, Vision).<br>- **Reliability**: Prevents orders that cannot be supported operationally.<br>- **Maintainability**: Allows future expansion by changing configuration, not core logic. |
| **US-21 — Commission Calculation (Internal)**: As a **Platform Operator**, I want to **calculate expected commission per restaurant based on GMV**, so that **financial reporting is consistent**. **[QAs: Reliability, Testability, Maintainability]** | - Given an order is marked `Delivered`, when the final paid amount is recorded (COD collected by shipper, or VNPay-paid amount confirmed by the gateway), then GMV and commission are calculated using the configured fixed percentage (BR-5).<br>- Given the commission rate changes, when configuration is updated, then the system uses the new rate only for orders delivered after the change, and each delivered order stores a snapshot of the commission rate used so historical records remain unchanged.<br>- Given rounding rules, then calculations follow consistent rounding to currency precision. | Reliability; Testability; Maintainability | - **Reliability**: Financial correctness is non-negotiable (BR-5).<br>- **Testability**: Deterministic calculations should be unit-tested with edge cases.<br>- **Maintainability**: Commission policies may evolve; logic should be easy to adjust safely. |

## Notes (configuration-based measurability)

Several acceptance criteria use **configuration-based thresholds** (timeouts, SLAs, “stuck” detection). This keeps them measurable/testable while letting you tune values during MVP.

You can finalize and document these configuration values for your project:
- Notification/real-time SLAs per role and network baseline.
- Restaurant accept timeout and per-status “stuck” thresholds.
- Service area boundary representation (polygon, radius, administrative region).
