Quality Attributes (QAs) referenced use the course taxonomy: **Usability, Performance, Availability, Reliability, Scalability, Security, Interoperability, Manageability, Supportability, Testability, Maintainability, Flexibility, Conceptual Integrity, Reusability**.

> Note on format: Each story ends with an explicit QA list: `[QAs: ...]`.

---

## User Stories (Grouped by Role)

### Planning fields

- **SP (Story Points)**: Fibonacci scale (1, 2, 3, 5, 8, 13) for relative effort.
- **Priority (MoSCoW)**: `Must` (MVP core), `Should` (MVP important), `Could` (post-MVP), `Won’t` (explicitly deferred).

| US-1 | **US-1 — Customer Registration/Login**: As a **Customer**, I want to **register and log in to the app**, so that **I can place and track orders with my profile**. **[QAs: Security, Usability, Availability]** | - Given I am not logged in, when I submit valid registration details, then my account is created and I can log in immediately.<br>- Given I enter invalid credentials, when I attempt to log in, then I am denied access and shown a clear error without exposing sensitive details.<br>- Given I am logged in, when I update my basic profile fields (e.g., display name, phone number), then changes are saved and reflected on my next app launch.<br>- Given the auth service is unavailable, when I attempt to log in, then I receive a retryable error and the app does not crash. | Security; Usability; Availability | - **Security**: Login is the gatekeeper for customer identity and order ownership; if the system cannot resist unintended actions (e.g., unauthorized access), attackers can take over accounts, view personal data, and place fraudulent orders—directly harming trust, retention, and causing support/financial loss.<br>- **Usability**: Registration/login sits at the top of the conversion funnel; confusing validation or unclear errors increases drop-off before the first order and reduces repeat usage, so the flow must be straightforward and self-correcting under normal user mistakes (wrong password, missing fields).<br>- **Availability**: Authentication unavailability blocks every revenue-generating action (browse → add to cart → checkout requires identity); even short downtime translates into immediate lost orders and churn because users cannot enter the system when intent is high. | 5 | Must | Foundation for identity, order ownership, and role-based actions. |

| US-4 | **US-4 — View Restaurant Availability**: As a **Customer**, I want to **see whether a restaurant/menu item is available**, so that **I do not waste time ordering unavailable items**. **[QAs: Reliability, Usability, Performance]** | - Given a restaurant is marked Closed/Unavailable, when I open it, then the UI clearly indicates unavailability and blocks adding items to cart.<br>- Given a menu item is marked Sold Out, when I view the menu, then the item is not addable to cart.<br>- Given availability changes while I browse, when the change is received, then the UI updates within a defined window (e.g., ≤ 10 seconds) or on refresh. | Reliability; Usability; Performance | - **Reliability**: Availability is a correctness-critical signal; if it is wrong, customers invest time building carts that later fail, increasing abandonment, cancellations, and support contacts—reducing trust and repeat purchases.<br>- **Usability**: Clear “Closed/Sold Out” cues and blocked actions prevent confusion and repeated failed attempts, keeping the ordering journey smooth and protecting conversion.<br>- **Performance**: The value of availability depends on timely response; if updates are delayed beyond the stated window, customers act on stale state and experience failure, so the system must reflect changes within a measurable time period. | 3 | Must | Depends on partner availability controls (US-12). |

Reliability here directly protects completion rate and operational stability.<br>- **Interoperability**: Address validation typically depends on external geocoding/maps; integration problems must be detected and handled explicitly. Without dependable interaction, the system risks wrong distance calculations and incorrect accept/reject decisions.<br>- **Usability**: When the system blocks checkout, customers need a clear explanation and next action (change address or choose another restaurant). Poor feedback causes repeated failures, frustration, and churn at the most sensitive step of the buying flow. | 5 | Must | Depends on map/geocoding/distance capability; ties to BR-3 and service area policy (US-20). |
| US-7 | **US-7 — Checkout With COD or VNPay (MVP)**: As a **Customer**, I want to **place an order using COD or VNPay**, so that **I can complete purchases with my preferred payment method**. **[QAs: Security, Usability, Reliability, Interoperability, Flexibility]** | - Given I have items in my cart, when I proceed to checkout, then I can select either COD or VNPay as the payment method (BR-4).<br>- Given I select COD, when I confirm the order, then an order record is created with status `Pending` and an order ID is returned.<br>- Given I select VNPay, when I confirm the order, then the system initiates the VNPay payment flow and only creates/routes the order after receiving a successful payment confirmation from VNPay (BR-4).<br>- Given VNPay payment fails or is cancelled, when the VNPay flow returns to the app, then the order is not routed and the user sees a clear failure/cancellation state with a retry option.<br>- Given I retry the same checkout with the same client idempotency key within a configured TTL (e.g., `ORDER_IDEMPOTENCY_TTL_MINUTES`), when the request reaches the backend, then the system returns the same order ID and does not create a duplicate order. | Security; Usability; Reliability; Interoperability; Flexibility | - **Security**: Checkout is where money and order creation intersect; if the system cannot resist unintended actions (e.g., forged callbacks or tampered payment results), it enables fraud, chargebacks, and disputes that directly damage revenue and platform credibility.<br>- **Usability**: Payment is the most abandonment-prone step; unclear COD/VNPay choice, confusing failure states, or poor feedback increases drop-off and reduces completed orders. A clear, guided flow improves conversion and repeat purchasing.<br>- **Reliability**: Orders and payments must remain consistent over time; without reliable idempotency and state handling, customers can be charged twice or create duplicate orders, causing refunds, support costs, and long-term trust loss.<br>- **Interoperability**: VNPay introduces external interactions and callbacks; the system must handle the gateway’s responses predictably, or checkout becomes fragile and causes failed payments and lost sales.<br>- **Flexibility**: Payment methods evolve with market/partner needs; if checkout is not adaptable, adding a new provider becomes a risky redesign that delays business expansion and slows time-to-market. | 13 | Must | Depends on cart (US-22), constraints (US-5), deliverability (US-6), and lifecycle (US-8). VNPay requires gateway integration and confirmation handling. |
| US-9 | **US-9 — Real-Time Order Status Updates**: As a **Customer**, I want to **receive real-time order status updates**, so that **I can track progress without repeatedly refreshing**. **[QAs: Availability, Performance, Interoperability, Reliability]** | - Given my order status changes, when the backend publishes an update, then my app receives the update within a defined SLA (e.g., ≤ 5 seconds under normal conditions).<br>- Given the app is in the background or closed, when a critical status update occurs, then the system delivers a push notification via APNs/FCM and the app reflects the latest status on next open (FR-2.3).<br>- Given the real-time channel disconnects, when reconnect occurs, then the app resynchronizes status to the latest state.<br>- Given push/WebSocket providers are degraded, then the system falls back to periodic polling without breaking the app. | Availability; Performance; Interoperability; Reliability | - **Availability**: Tracking is a trust feature; if it is frequently unavailable, customers feel the platform is unreliable, increasing anxiety, complaints, and churn—especially during delivery windows when support load is highest.<br>- **Performance**: “Real-time” has a measurable meaning; updates delivered outside the SLA (e.g., > 5 seconds) become stale and drive manual refreshing and support contacts, weakening user experience and retention.<br>- **Interoperability**: Push notifications and WebSocket/polling mechanisms are external or infrastructural dependencies; robust interaction is required to deliver updates across device states (foreground/background) and network conditions.<br>- **Reliability**: Status must remain correct over time (no missing transitions, no conflicting states). If the system delivers wrong status or fails to resync after disconnects, customers lose confidence, disputes increase, and operational teams spend more time investigating “where is my order” incidents. | 8 | Must | Depends on lifecycle events (US-8) and updates from restaurant/shipper actions (US-13, US-16, US-17, US-23). |
| US-22 | **US-22 — Shopping Cart Management (MVP)**: As a **Customer**, I want to **add/remove items and adjust quantities in my cart**, so that **I can review my order before checkout**. **[QAs: Usability, Reliability, Performance]** | - Given I am viewing a menu item, when I add it to my cart with a quantity, then the cart updates and the running total is recalculated.<br>- Given my cart contains an item, when I increase/decrease quantity or remove the item, then the cart updates immediately and totals reflect the change.<br>- Given I leave and reopen the app, when I return to the cart, then the cart contents remain available (within a configured persistence window) or I am clearly informed the cart was reset.<br>- Given my cart contains items from one restaurant, when I attempt to add an item from a different restaurant, then the system enforces the single-restaurant constraint as defined in US-5 (BR-2). | Usability; Reliability; Performance | - **Usability**: Cart edits are frequent and directly influence purchasing decisions; if interaction is confusing or feedback is unclear, customers hesitate, make mistakes, and abandon checkout—reducing conversion.<br>- **Reliability**: The cart is the “source of truth” for what will be charged; inconsistent quantities/totals across actions or app reopen leads to incorrect orders and payment disputes, increasing refunds and support cost while damaging trust.<br>- **Performance**: Cart updates and recalculation must respond within a tight time window; sluggish updates make the app feel broken and interrupt the checkout momentum, which is strongly correlated with drop-off and lost revenue. | 5 | Must | Depends on menu/catalog (US-11) and rule enforcement (US-5). |

## Shipper (Delivery Personnel)

| ID | User Story | Acceptance Criteria | Quality Attributes | Justification | SP | Priority (MoSCoW) | Key Dependencies / Notes |

| US-14 | **US-14 — Shipper Onboarding Approval**: As a **Delivery Personnel (Shipper)**, I want to **be approved by an Admin**, so that **I can receive delivery jobs**. **[QAs: Security, Manageability, Supportability]** | - Given I register as a shipper, when submission completes, then my account is `Pending Approval` (BR-1).<br>- Given an admin approves, then I can toggle availability and receive dispatch requests.<br>- Given an admin rejects, then I cannot receive jobs and I receive a reason. | Security; Manageability; Supportability | - **Security**: Approval is the gate for a role that can see delivery addresses and affect fulfillment state. If the system cannot resist unintended activation or identity misuse, malicious shippers can access sensitive data and tamper with order progress, driving fraud, safety incidents, and rapid loss of marketplace trust (BR-1).<br>- **Manageability**: Approval must work as an operational pipeline, not a one-off feature—admins need facilities to review a queue, change shipper status, and detect stuck cases fast. | US-15 | **US-15 — Shipper Availability Toggle**: As a **Shipper**, I want to **set myself available/unavailable**, so that **I only receive orders when I’m ready to deliver**. **[QAs: Usability, Reliability, Performance, Security]** | - Given I set status to `Available`, then I become eligible to receive dispatch requests within a defined SLA (e.g., ≤ 10 seconds).<br>- Given I set status to `Unavailable`, then I stop receiving new dispatch requests immediately (or within SLA).<br>- Given intermittent connectivity, when I change status, then the app confirms whether the change is synced or queued. | Usability; Reliability; Performance; Security | - **Usability**: Toggling availability is a frequent, time-sensitive action (starting/ending a shift, pausing mid-route). The UI must make state and outcome unmistakable (available/unavailable; synced vs queued), otherwise shippers unintentionally accept jobs they can’t fulfill or miss jobs they intended to take—hurting delivery success rate and shipper earnings.<br>- **Reliability**: Availability is a persistent runtime state that must remain correct over time across restarts and flaky networks. If client/server states diverge, dispatch targets the wrong pool (offers sent to unavailable shippers or withheld from available ones), causing missed pickups, longer ETAs, and lower customer satisfaction.<br>- **Performance**: The ≤ 10 seconds SLA is the response measure for when eligibility takes effect. If propagation is slow, dispatch decisions are made on stale availability, increasing wasted offers and reducing throughput precisely during peak ordering windows.<br>- **Security**: Because availability affects assignment and income, the system must resist unintended actions (unauthorized toggles, replayed requests). Without this, attackers can sabotage a shipper’s availability or manipulate dispatch fairness, creating operational disruption and fraud risk. | 3 | Must | Needed before dispatch/assignment can be meaningful. |
| US-16 | **US-16 — Shipper Accept & Pick Up Order**: As a **Shipper**, I want to **accept a delivery job and confirm pickup**, so that **the customer can track the delivery accurately**. **[QAs: Reliability, Security, Interoperability, Performance]** | - Given I receive a dispatch request, when I accept, then the order is assigned to me and cannot be assigned to another shipper simultaneously.<br>- Given I arrive at the restaurant, when I confirm pickup, then order status transitions to `Picked Up` (part of BR-7 lifecycle).<br>- Given my app cannot reach the server, when I attempt to confirm pickup, then the system does not transition the order state and the app shows a retryable error message. | Reliability; Security; Interoperability; Performance | - **Reliability**: This story is defined by correct, durable state transitions over time: accepting must be atomic (no double-assignment) and pickup confirmation must be idempotent under retries (no duplicate/missing transitions). - Restaurant accept timeout and per-status “stuck” thresholds.
